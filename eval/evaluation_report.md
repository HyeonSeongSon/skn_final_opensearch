# 검색 품질 평가 리포트

내부규정 검색 시스템(`opensearch_api.py` + `opensearch.py`, 하이브리드 BM25+벡터 검색 + BGE 리랭커)의 검색 품질을 정량적으로 측정하기 위해 진행한 작업을 정리한다.

## 1. 배경

`data/*.jsonl`(제약회사 내부규정 5개 문서)을 OpenSearch에 색인하는 과정에서, welfare(복리후생) 문서의 경조사/학자금 지원 조항이 "결혼:", "사망:" 같은 헤더와 하위 항목이 서로 다른 줄로 분리되어 있어 헤더 없이는 의미가 반토막 나는 구조적 문제를 발견했다(`preprocess_documents.py`로 수정, `data/processed/*.jsonl` 생성). 이 수정이 실제로 검색 품질을 개선하는지 **측정할 방법이 없다는 문제**가 있어 평가 하네스를 구축하게 되었다.

## 2. 평가 방법론

### 2.1 평가 지표
- **Recall@1 / @3 / @5**: 정답이 상위 1/3/5개 결과 안에 포함되는 비율
- **MRR (Mean Reciprocal Rank)**: 정답이 나온 순위의 역수 평균

### 2.2 질의 유형 설계
청크(조항) 하나당 **exact 1개 + paraphrase 1개를 고정 쌍(paired)으로 생성**하기로 했다. 유형별로 개수를 자유롭게 생성하게 두는 대안도 검토했으나, "같은 청크에서 나온 쌍으로 유형 간 성능을 직접 대조"할 수 있어야 진단력이 높다고 판단해 고정 쌍 방식을 채택했다.

- **exact**: 조항의 키워드/조 제목을 그대로 활용한 직접적인 질문 (BM25 친화적)
- **paraphrase**: 같은 내용을 다른 표현으로 묻는 질문, 핵심 키워드 회피 (벡터 검색 친화적)
- **collision**: 전처리로 수정한 헤더 병합 케이스를 표적 검증하기 위해 직접 작성한 대조 질의 (예: "결혼 시 본인 경조금"과 "사망 시 본인 경조금"처럼 반대 답을 요구하는 쌍)

### 2.3 정답 판정 방식
같은 조(예: welfare 제4조 경조사 지원) 아래 여러 하위 항목(결혼/출산/사망/기타)이 존재하기 때문에 `(문서명, 장, 조)`만으로는 정답을 특정할 수 없다. 그래서 정답 판정 키를 `(문서명, 장, 조, snippet)`으로 설계했다 — `snippet`은 해당 청크의 `문서내용` 중 형제 항목과 겹치지 않는 최소 고유 접두사로, 반환된 검색 결과의 `문서내용`에 이 부분 문자열이 포함되어야 정답으로 인정한다.

## 3. 평가 데이터셋 구축

### 3.1 자동 생성 (`eval/generate_questions.py`)
- `data/processed/*.jsonl`에서 `장`/`조`가 둘 다 null인 순수 제목 행만 제외하고 230개 청크를 대상으로 함
- `ChatOpenAI(gpt-4o)` + `ChatPromptTemplate`로 청크당 exact/paraphrase 질문을 JSON 배열로 생성 (기존 `opensearch.py`의 `get_keyword()` 호출 관례를 따름, `OpenSearchClient`는 인스턴스화하지 않아 임베딩/리랭커 모델 로딩 없이 가볍게 실행)
- JSON 파싱 실패 시 1회 재시도, 그래도 실패하면 스킵 (230개 중 1개 최초 실패 → `eval/retry_skipped.py`로 재시도해 100% 복구)
- 결과: **460개 질의** (`eval/generated_questions.jsonl`)

### 3.2 품질 검증 및 수정
생성된 질의를 검토하던 중, 같은 조 안의 서로 다른 항목인데 `"제9조 금품 등의 수수 제한에 대해 알고 싶습니다."`처럼 **조 제목만 되풀이하는 동일한 질문이 여러 항목에 중복 생성**된 걸 발견했다(38개 행, 전체의 16.5%). doc_id가 같은 형제 항목은 검색 결과에 하나만 살아남을 수 있어(§5.1), 질문까지 똑같으면 구조적으로 항상 하나는 미스 처리되는 문제였다.

`eval/fix_ambiguous_questions.py`로 해당 행에 한해 "같은 조의 다른 항목들"을 프롬프트에 함께 제공하고 겹치지 않는 질문을 요구하도록 재생성 → 중복 0건으로 해소.

### 3.3 수작업 collision 질의 (`eval/collision_questions.jsonl`)
LLM 자동 생성은 우연히 헷갈리는 질문을 만들 수는 있어도, 의도적으로 "결혼 vs 사망처럼 정반대 답을 요구하는 대조쌍"을 만들지는 않는다. 그래서 실제 `data/processed/*.jsonl` 내용을 근거로 **10개를 직접 작성**했다:
- welfare 제4조(경조사 지원): 결혼/출산/사망/기타 6건 (결혼↔사망, 자녀 항목 등 반대 방향 대조쌍 포함)
- welfare 제5조(학자금 지원): "지원 내용"(대학교) vs "자녀 수 제한" 구분 2건
- compliance 제14조(자사제품설명회): "가./나." 항목 구분 2건

최종 평가셋 규모: **470개 질의** (exact 230 + paraphrase 230 + collision 10)

## 4. 평가 인프라 (`eval/run_search_eval.py`)
`POST /search`를 호출해 §2.3의 매칭 규칙으로 hit@1/3/5, MRR을 계산하고 `query_type`별로 집계한다. `--no-rerank`, `--index-name`, `--top-k`, `--rerank-top-k` 등을 옵션화해 다양한 조건을 비교할 수 있게 했다. 상세 결과는 `eval/eval_results*.jsonl`에 기록되어 실패 사례를 개별 확인할 수 있다.

## 5. 평가 과정에서 발견하고 수정한 버그

### 5.1 doc_id 충돌 버그 (`opensearch.py`, `normalized_hybrid_search`)
첫 평가 실행에서 collision 유형 10건이 **전부(Recall@5=0)** 실패했다. 원인을 추적한 결과, BM25/벡터 결과를 병합하는 코드가 `doc_id = 문서명+장+조`(문서내용 미포함)를 키로 쓰는 딕셔너리에 무조건 덮어쓰기를 하고 있었다([opensearch.py:465,479](../opensearch.py)) — 같은 조 아래 여러 형제 항목이 있으면 그중 하나만 검색 결과에 살아남고, 어느 것이 살아남는지는 관련도가 아니라 OpenSearch가 반환한 순서에 따른 우연이었다.

**수정**: OpenSearch가 색인 시 자동 부여하는 고유 `_id`를 병합 키로 사용하도록 변경(`search_document()`가 `hit["_id"]`도 반환하도록 수정). 재색인 불필요(검색 시점 병합 로직만의 문제). 부수적으로 BM25/벡터 쿼리의 하드코딩된 `"size": 10`도 함수 인자 `top_k`에 연동하도록 수정.

수정 후 collision Recall@5가 **0% → 100%**로 상승 — 헤더 병합 전처리(§1)의 실제 효과가 이 버그에 가려져 있었음이 확인됐다.

### 5.2 `--use-rerank` CLI 옵션 버그
`eval/run_search_eval.py`의 `--use-rerank` 옵션이 `action="store_true", default=True`로 정의되어 있어 CLI로 끌 방법이 없었다. `--no-rerank`로 교체해 리랭크 유무를 실제로 비교할 수 있도록 수정.

## 6. 평가 결과

### 6.1 doc_id 버그 수정 전 / 후 (문서내용만 임베딩, 리랭크 적용)

| query_type | N | 수정 전 R@1/@3/@5/MRR | 수정 후 R@1/@3/@5/MRR |
|---|---|---|---|
| ALL | 470 | 0.372 / 0.404 / 0.411 / 0.388 | 0.845 / 0.964 / 0.991 / 0.906 |
| exact | 230 | 0.283 / 0.300 / 0.300 / 0.291 | 0.857 / 0.970 / 0.996 / 0.917 |
| paraphrase | 230 | 0.478 / 0.526 / 0.539 / 0.503 | 0.835 / 0.957 / 0.987 / 0.896 |
| collision | 10 | 0.000 / 0.000 / 0.000 / 0.000 | 0.800 / 1.000 / 1.000 / 0.883 |

버그 수정 전에는 paraphrase가 exact보다 높은 역전 현상이 있었는데(exact 질의가 조 제목 등 조 필드 매치를 더 많이 유발해 doc_id 충돌도 더 자주 일으켰던 것으로 추정), 수정 후에는 정상적으로 exact가 paraphrase를 근소하게 앞서는 패턴으로 돌아왔다.

### 6.2 남은 실패 케이스 분석 (문서내용만 임베딩, 리랭크 적용 기준)
470건 중 완전 실패(Recall@5=0)는 **4건(0.85%)**. 각 사례를 리랭크 이전 후보군(top_k=20)에 정답이 있었는지까지 확인해 원인을 구분했다.

| 케이스 | 후보군에 정답 있었나 | 원인 |
|---|---|---|
| "제2조 정의에 대해 알고 싶습니다." | 있음 (5/20위, 같은 조 후보 9개) | 정답 청크가 실질 내용 없는 도입부 문장이라 질문 자체가 모호함 — **평가 데이터 한계** |
| "컴플라이언스 책임자의 역할은?" | 있음 (3/20위) | "책임자"라는 일반 단어 때문에 완전히 다른 문서("공시책임자")로 리랭커가 쏠림 — **임베딩/리랭커 한계** |
| "공시 관련 업무를 하는 부서는?" | 있음 (6/20위) | "사업부서"와 "공시담당부서"라는 근접 개념의 혼동 — **정답 라벨링 자체의 모호성** |
| "CEO가 공시 관리에서 맡은 책임은?" | **없음** (top_k=50에서 24위로 확인) | 진짜 후보군 탈락 — **top_k 파라미터 문제, 유일하게 top_k 확대로 개선 가능** |

즉 4건 중 3건은 top_k를 늘려도 소용없는 리랭커/임베딩·라벨링 한계이고, 1건만 `top_k`를 20→30 수준으로 늘리면 해결될 수 있는 파라미터 문제였다 (아직 미적용, 개선폭 대비 우선순위가 낮다고 판단).

### 6.3 리랭커 Ablation (문서내용만 임베딩 기준)

| query_type | N | 리랭크 없음 | 리랭크 적용 |
|---|---|---|---|
| ALL | 470 | 0.777 / 0.911 / 0.949 / 0.851 | 0.845 / 0.964 / 0.991 / 0.906 |
| exact | 230 | 0.757 / 0.874 / 0.922 / 0.829 | 0.857 / 0.970 / 0.996 / 0.917 |
| paraphrase | 230 | 0.796 / 0.943 / 0.974 / 0.871 | 0.835 / 0.957 / 0.987 / 0.896 |
| collision | 10 | 0.800 / 1.000 / 1.000 / 0.883 | 0.800 / 1.000 / 1.000 / 0.883 |

리랭커는 exact 유형에 가장 크게 기여(+10.0%p R@1)하고, paraphrase에는 상대적으로 적게 기여(+3.9%p R@1). **collision 유형은 리랭커 유무와 완전히 동일** — 형제 항목을 구분해내는 효과는 리랭커가 아니라 doc_id 버그 수정 + 하이브리드 결합 단계에서 이미 완성된다는 뜻이다.

### 6.4 임베딩 텍스트 구성 실험: `문서내용`만 vs `문서명+장+조+문서내용` 결합
기존 색인 코드(`opensearch_api.py`)는 벡터 임베딩 시 `문서내용` 필드만 인코딩한다. `문서명+장+조`를 붙여서 임베딩하면 "가. 업무 전반에 대한 접근..." 같이 문맥 없이는 의미가 반토막 나는 청크의 벡터 품질이 개선될 것이라는 가설을 세우고, **기존 코드/인덱스는 건드리지 않고** 별도 스크립트(`eval/index_combined_embedding.py`)로 새 인덱스(`internal_regulations_index_combined`)에 결합 텍스트로 재색인해 비교했다 (`문서내용` 필드 자체는 원본 그대로 저장해 BM25 조건은 동일하게 유지, 벡터 임베딩 입력 텍스트만 변경).

| 임베딩 방식 | 리랭크 | ALL R@1 | ALL R@3 | ALL R@5 | ALL MRR |
|---|---|---|---|---|---|
| 문서내용만 | 없음 | 0.777 | 0.911 | 0.949 | 0.851 |
| 문서내용만 | 있음 | 0.845 | 0.964 | 0.991 | 0.906 |
| 결합 | 없음 | 0.845 | 0.964 | 0.994 | 0.907 |
| 결합 | 있음 | **0.851** | **0.970** | 0.994 | **0.909** |
